# 动画德州：不限改造项数量的委托任务书与验收标准

日期：2026-10-22。用途：Owner 可直接交给其他模型执行。本文件仅定义委托与验收，本轮没有实施业务改造。

项目：`D:\workspace\projects\anitexas`。

## 1. 你要交付什么

把动画德州改造成一款朋友能顺畅进入、一起开始、看懂每轮行动、理解结果并愿意继续玩的游戏。四个重点同等重要：

1. 对局中知道看什么、轮到谁、自己能做什么。
2. 首页、建房、邀请、加入、等人和准备顺畅。
3. 游戏节奏与结算清楚，有明确且不过度的反馈。
4. 不抢先开局、不擅自补机器人；文案简洁，组件协调，布局可用。

**不设改造项数量上限，也不要求凑到某个数量。** 已有 200 项是起始清单，不是发现问题的边界，也不是 200 个必须新建的组件。你必须真实运行并体验当前版本，发现清单外阻碍上述目标的问题时继续修复。已有能力若验证可靠，应保留；关联项应合并实现。不得为了增加条目拆分同一问题、制造无关功能或重写已正常工作的模块。

允许超过 200 项；不接受仅靠增加项目数、提示文字、特效或测试数量宣称体验更好。完成依据是后文验收门槛。

## 2. 阅读顺序与优先关系

先阅读本文件，再读 [200 项改造清单](04-redesign-200-2026-10-22.md)，其后按需查阅旧版设计、协议与源码。最新 Owner 指令优先；本文件与 200 项清单中的第二轮政策覆盖旧交接文件中相冲突的自动开局策略。

开工检查当前 HEAD、git status、适用 AGENTS.md、实际依赖和数据。不要假设历史报告代表现在状态。此前报告说缺少卡池，本次审查已经看到 `data/cards.json`，应重新确认其可用性。用户已有文件、未提交修改与数据库不得被清理或覆盖。

## 3. 必须执行的产品政策

### 朋友房

- 创建、加入、刷新、恢复连接、玩家准备均不得启动第一手。
- 默认机器人关闭；空座表示等待朋友，不自动成为机器人。
- 玩家准备与房主开始是独立操作。全员准备只是满足条件，不自动发牌。
- 第一手和下一手均由房主明确点击开始。默认手动续局。
- 房主可明确调整目标人数后以当前人数开始，仍须满足真实参局人数等合法条件；不能以补机器人替代人数不足。
- 添加机器人是明确可见的房主选择，不能藏在预设或回退逻辑里。
- 房主身份由服务端确认，按钮隐藏不能代替权限校验。

### 练习房

- 使用独立入口，与朋友房区别清楚。
- 创建前说明机器人数量；自动续局必须是明示选择。
- 自动续局的暂停、取消与倒计时由服务端决定，客户端不得假装暂停成功。

两种房间的策略必须贯穿 REST、WebSocket、定时器、mock、恢复逻辑和测试。尤其不能修了前端按钮却保留后台自动开局。

## 4. 执行边界

本次授权范围是本地项目体验改造、必要的协议与服务端配合、测试、设计产物和交付文档。不要自动部署服务器、购买服务、修改无关项目或发布外部内容。

保留既有扑克规则、牌型比较、筹码与积分规则、隐藏信息边界。改变这些规则不属于一般体验修复；发现必须改规则才能解决的问题时，记录具体方案和影响，交 Owner 决定。

优先复用现有 React/Go 技术栈和 v2 权威状态框架。允许为开局权限、房间策略、取消准备及必要恢复流程增加字段或命令；不要以“不限数量”为由迁移框架或引入完整账户、商城、观战、排行榜等无关大系统。

自主处理正常设计与实现细节，不需要逐项请求批准。遇到确实缺少关键产品决策、可能损害已有数据或需要范围外操作时，说明影响并提出具体问题；同时继续不依赖该答案的工作。

## 5. 工作流程：先看真实游戏，再设计和实现

### 第一步：建立当前体验基线

运行真实后端与前端，用两个独立身份完成至少一手。记录首页、建房、等待、本人行动、结算五个关键画面与实际问题。核对抢先开局到底来自 create、join、ready、残留定时器还是演示模式，保留经过脱敏的事件链，不凭猜测修改。

使用隔离测试数据库；需要测试卡池时优先使用已有合法数据或项目 fixture。不要覆盖用户数据库。若只能使用受控 fixture，明确标注；fixture 可以验证真实后端链路，不能冒充正式卡池的内容体验。

### 第二步：先确定关键页面布局

完成首页、朋友准备室、本人行动、结算四张实际目标视口的设计样张或可运行原型，标明主要操作和信息层级。对照基线检查是否减少了重复内容与视线移动。

样张不是新的装饰任务。核心是确定：玩家先看哪里、下一步点哪里、手牌和操作是否同时可见。无需等待 Owner 例行批准即可继续在本地实现；有新增方向性争议再提问。

### 第三步：实施完整主流程

按“开局控制 → 首页/邀请/准备室 → 对局布局与操作 → 结算/续局 → 异常恢复与视觉打磨”推进。四个重点都必须落地，不能只完成后端协议就停止，也不能把未完成的状态修复藏在漂亮界面下。

### 第四步：持续体验并修正

每完成一段主流程，用真实页面回走该段，发现清单外问题继续登记修复。不要机械地等所有代码写完才第一次打开浏览器。

新增问题从 201 起编号，注明来源为用户反馈、真实复现、源码确认或设计改进；记录实际场景、影响与验收方式。重复问题合并引用，不重复计数。原 001–200 保留编号，不悄悄删掉难项。

## 6. 硬性验收：全部通过才能宣称完成

以下测试使用真实后端。两个玩家使用独立浏览器上下文或独立会话存储，不以共享身份的两个标签页代替。界面截图必须来自实现，不能以设计图替代。

| 编号 | 操作步骤 | 通过标准 |
|---|---|---|
| H01 建房不抢跑 | A 创建默认朋友房，独处 60 秒，再点击准备并等待 60 秒 | 仍在准备室；没有第一手、盲注或机器人；按钮没有隐式开始 |
| H02 朋友加入 | B 用邀请链接加入；A/B 准备，等待至少 15 秒 | 人数与状态两端一致；全员准备仍未开局；仅 A 可开始 |
| H03 主动开局 | A 点击开始；重复发送同一开始请求；B 尝试越权开始 | 恰好一手；重复请求不重复发牌；越权拒绝；初始筹码与盲注正确 |
| H04 人数与机器人 | 目标 4 真人但只有 2 真人，尝试开始；明确调整目标或添加机器人后再试 | 未经明确变更不能偷偷补人；变更后的名单、人数与开局条件一致 |
| H05 首页与深链 | 首次访问建房；另一身份直接打开邀请；输错码、满房各试一次 | 不需进入建房表单才能加入；错误就地可恢复；不重复建房或占座 |
| H06 准备可控 | B 准备后取消；A 此时开始；再恢复准备 | 取消真实生效，A 看到原因；服务端不能用过时 ready 开始 |
| H07 普通四轮 | 真实完成底牌下注、翻牌、转牌、河牌、摊牌 | 阶段、公共牌、行动者、筹码均一致；换街本轮投入清零；操作区不显示非法动作 |
| H08 金额正确 | 覆盖已有投入、加注、短码跟注、短全下不重开加注 | “加到”与“再投入”正确；总上限正确；非法加注无法提交 |
| H09 特殊结束 | 分别完成其他人全弃牌、全下直发、平分或多人获奖 | 没有假等待轮次；胜因与真实结果一致；不误标唯一赢家 |
| H10 手动下一手 | 朋友房结算后停留超过旧自动延时；所有人准备但房主不开始 | 不自动进入下一手；上手结果可关闭再打开；房主点击后才开始 |
| H11 练习自动续局 | 明示选择自动续局，结算后暂停；恢复该策略再测试倒计时 | 暂停由服务端确认且旧定时器失效；两端显示同一策略和时刻 |
| H12 断线与刷新 | 行动中断线再恢复；结算中整页刷新；旧短券过期后恢复 | 不换身份、不重复动作；可恢复结果与阶段；无法恢复时有明确退出/重入路径 |
| H13 提交不确定 | 发动作后丢失回执，触发核对；期间其他玩家有事件 | 不被无关事件解锁；不盲目重发；最终状态与实际执行结果一致 |
| H14 权限与隐私 | 多视角检查底牌、私看、弃牌未公开牌、历史与恢复帧 | 只含接收者有权看到的信息；公开日志和截图不含恢复凭据 |
| H15 布局 | 1366×768、1920×1080、390×844；覆盖 4/6/9 座和金额面板展开 | 无遮挡、误溢出或整页缩小；手机不横向拖大桌找自己；本人底牌与主操作持续可访问 |
| H16 离席与关闭 | 房主断线恢复、房主离开、玩家离席、房间关闭各测一次 | 没有无主可开局漏洞、旧连接误踢新连接或永久假等待；关闭后无旧定时器启动 |
| H17 连玩三手 | 两个真人连续完成邀请开局、三手、回顾结果、离开 | 无需刷新解卡；准备和开始不串手；状态与历史不混人、不混手 |

H15 的桌面主操作需在首屏且无需上下滚动寻找；手机允许次要信息纵向滚动，但操作条与自己的牌应形成可直接访问的连续区，不能用缩小到不可读满足“一屏”。不得使用浏览器缩放来伪造目标视口通过。

H01/H02/H03/H10/H14 是阻断项：任何一个失败都不能交付为完成。其他硬性项也必须通过，环境不支持时应标未验证而非跳过后宣称全部完成。

## 7. 体验验收：不能只靠自动化证明

### 信息和操作

在本人回合、等待别人、已弃牌、已全下、结算五个状态，让未读实现文档的试玩者回答：现在第几手/哪个阶段，轮到谁，我能做什么，接下来如何继续。目标为每个状态 5 秒内找到答案，无需实施者口头指路。

有真实试玩者时记录实际观察；没有试玩者时，用浏览器走查核验信息位置，并明确标“理解速度待 Owner 验收”，不能编造用户测试结论。不可把 5 秒理解目标写成已被单元测试证明。

### 文案

- 用户界面不出现协议名、权威帧、受控项、mock 开关、开发编号或调试建议。
- 每个普通状态保留一句主说明；确有风险、费用或身份影响才增加必要说明。
- 同一事实不在顶栏、进度条、状态卡和操作栏重复四遍。
- 等待必须说明真实等待对象或原因；按钮名称必须对应实际效果。

### 视觉

- 四个关键页面有一致的字号、按钮、间距和层级；不能仅给旧页面添加更多带边框 Panel。
- 主动作明显，工具入口降级；危险动作与主动作位置和样式清楚。
- 对局第一视觉重点是牌与行动，不是装饰、长说明或后台式数据卡。
- 长昵称、长作品名、封面失败、错误信息出现时仍不破坏布局。
- 阶段、金额、结果等关键文字清晰可读；色彩、音效和动画不是唯一信息来源。

视觉审美由 Owner 最终判断；实施者需给同视口前后对照，说明删了什么、重排了什么、如何减少寻找操作的成本，不把“我觉得好看”当验收证据。

## 8. 工程检查与证据

执行与变更相关的测试，并完成前端测试和生产构建、后端测试。针对开局权限、幂等、取消排程、恢复与隐藏信息增加有行为意义的回归测试。能运行 Go race 时执行；不能运行则记录工具链限制与替代检查，不声称 race 通过。

测试命令应以当前项目实际脚本为准。失败区分改造引入、已有失败和环境问题，分别记录，不以“不是这次改的”一笔带过。已通过后无需无理由反复跑同一批测试。

本地证据至少包括：

- 五个基线画面与四个改造后关键页面的同视口对照。
- 三个目标视口下本人行动、金额展开、结果的截图。
- 一段或分段真实双身份主流程记录，能追溯 H01–H17 的实际结果。
- 自动化测试命令、结果、关键测试名和失败原因。
- 每项完成状态对应的代码位置或证据路径。

截图、日志与录屏可以放隔离的本地验收目录；不要把大体积临时产物、敏感凭据或用户数据库提交到版本库。报告使用可点击的本地路径。

## 9. 完成标准与停止条件

只有在四个重点均完成、硬性验收通过、重大体验阻碍已解决且剩余限制被如实记录时，才可以将工程改造标为完成。Owner 的主观视觉与理解速度反馈单独列为待用户验收，不能伪造为已确认。

“不限数量”不等于永远不结束：当主流程已顺畅、所有硬门槛通过、没有新发现的阻断问题时停止扩展，不继续为颜色微差或无关功能无限迭代。

如果仍有阻断问题，应报告未完成及具体原因；已经完成的可审查改动照常交付。不要把未验证、已实现待测、不适用全部归入完成。
